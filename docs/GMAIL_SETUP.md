# Local Gmail recovery delivery

The user selected an external email provider and a Gmail sender on October 20, 2026. Task 3.4c.3a adds a standalone Gmail SMTP adapter; it does not activate recovery endpoints or change account eligibility. The existing synthetic recovery service retains its test-only guard.

## Configuration

Use the ignored `.env.local` file for `GMAIL_USER`, `GMAIL_SENDER_NAME` and `GMAIL_APP_PASSWORD`. The selected sender details have been prepared locally without adding personal sender details to the tracked example. `.env.example` contains only empty/generic settings. Do not paste credentials into chat or commit them.

Google requires 2-Step Verification for app passwords. Create a dedicated application password using [Google's app-password instructions](https://support.google.com/accounts/answer/185833), then enter that credential in GMAIL_APP_PASSWORD locally. Use the app password, not the normal Google account password. Some account/security configurations do not offer app passwords; if unavailable, the next integration choice is OAuth2 rather than weakening account security. This adapter currently implements app-password authentication, not OAuth2.

Start the approved local HTTPS launcher so AUTH_ORIGIN and the local marker are configured. The mail configuration refuses production mode, hosted/HTTP origins, non-Gmail sender mailboxes, missing/malformed app credentials and control characters in the sender name. Importing or constructing the adapter opens no network connection. Its explicit ready method checks SMTP authentication without sending a message; send sends only the supplied recovery message.

## Transport and message boundary

Pinned Nodemailer sends over smtp.gmail.com:465 with immediate TLS, verified certificates, TLS 1.2 minimum, bounded DNS/connection/greeting/socket waits, no content logging and no file/URL content access. See [Nodemailer SMTP documentation](https://nodemailer.com/smtp) and [Google's SMTP settings](https://support.google.com/mail/answer/7104828). The sender/envelope are fixed to the configured Gmail mailbox. A single validated recipient and plain-text body are generated by code; callers cannot supply headers, attachments, HTML or arbitrary URLs.

Only the configured local HTTPS origin and exact /verify-email or /reset-password paths are allowed, with one canonical fragment token and no query, userinfo or extra fragment data. Messages state that the link opens the development server on the same computer. They describe the approved token lifetime and one-time use. The adapter validates SMTP acceptance of the intended recipient and maps provider errors to generic SERVICE_UNAVAILABLE without returning raw transport details.

Call send only after issuance commits. There is no automatic send retry: a lost SMTP acknowledgment can follow successful delivery, and blind retries can duplicate mail. This standalone adapter provides no durable queue or delivery guarantee. It must not be wired directly into a public request path until generic response/failure handling and the delivery contract are reviewed.

## Current acceptance and next integration

Unit tests use a mocked SMTP transport and synthetic addresses/credentials. They cover credential/configuration rejection, lazy startup, readiness, recipient/header injection, purpose/origin validation, provider failure sanitization, acceptance checks and no automatic retries. No live Gmail verification or email has been performed. Google may still reject a credential/account or sender at runtime; these checks do not prove delivery/inbox placement.

Real-user recovery remains disabled. Remaining work includes release blocklist provenance/coverage, guarded non-test service wiring, actual bounded/CSRF-protected recovery HTTP adapters, same-response account-enumeration defenses around provider failures, explicit deployment/readiness and controlled live acceptance. The sender/password alone does not approve hosted ingress or production release.
