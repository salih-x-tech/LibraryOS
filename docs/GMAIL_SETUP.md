# Local Gmail recovery delivery

The user selected an external email provider and a Gmail sender on October 20, 2026. Task 3.4c.3a adds a standalone Gmail SMTP adapter; it does not activate recovery endpoints or change account eligibility. The existing synthetic recovery service retains its test-only guard.

## Configuration

Use the ignored `.env.local` file for `GMAIL_USER`, `GMAIL_SENDER_NAME` and `GMAIL_APP_PASSWORD`. The selected sender details have been prepared locally without adding personal sender details to the tracked example. `.env.example` contains only empty/generic settings. Do not paste credentials into chat or commit them.

Google requires 2-Step Verification for app passwords. Create a dedicated application password using [Google's app-password instructions](https://support.google.com/accounts/answer/185833), then enter that credential in GMAIL_APP_PASSWORD locally. Use the app password, not the normal Google account password. Some account/security configurations do not offer app passwords; if unavailable, the next integration choice is OAuth2 rather than weakening account security. This adapter currently implements app-password authentication, not OAuth2.

Start the approved local HTTPS launcher so AUTH_ORIGIN and the local marker are configured. The mail configuration refuses production mode, hosted/HTTP origins, non-Gmail sender mailboxes, missing/malformed app credentials and control characters in the sender name. Importing or constructing the adapter opens no network connection. Its explicit ready method checks SMTP authentication without sending a message; send sends only the supplied recovery message.

## Transport and message boundary

Pinned Nodemailer sends over smtp.gmail.com:465 with immediate TLS, verified certificates, TLS 1.2 minimum, bounded DNS/connection/greeting/socket waits, no content logging and no file/URL content access. See [Nodemailer SMTP documentation](https://nodemailer.com/smtp) and [Google's SMTP settings](https://support.google.com/mail/answer/7104828). The sender/envelope are fixed to the configured Gmail mailbox. A single validated recipient and plain-text body are generated by code; callers cannot supply headers, attachments, HTML or arbitrary URLs.

Only the configured local HTTPS origin and exact /verify-email or /reset-password paths are allowed, with one canonical fragment token and no query, userinfo or extra fragment data. Messages state that the link opens the development server on the same computer. They describe the approved token lifetime and one-time use. The adapter validates SMTP acceptance of the intended recipient and maps provider errors to generic SERVICE_UNAVAILABLE without returning raw transport details.

Call send only after issuance commits. There is no automatic send retry: a lost SMTP acknowledgment can follow successful delivery, and blind retries can duplicate mail. This standalone adapter provides no durable queue or delivery guarantee. It must not be wired directly into a public request path until generic response/failure handling and the delivery contract are reviewed.

## Current acceptance and next integration

### Encrypted request-admission foundation

`createRecoveryRequestQueue` now records a durable request intent and mandatory audit in one transaction without reading users, checking eligibility, creating action tokens or contacting Gmail. It charges the approved shared recovery request budget before persistence. Known, ineligible and unknown addresses use the same operation path and record shape. A future HTTP response can report request receipt; it must not claim email delivery. This module is not wired into HTTP or a worker yet, so it does not resolve the full live-delivery gate.

The new `authRecoveryRequests` collection stores purpose, server-generated requestId, fixed-length ciphertext/nonce/tag, pending status and creation time. It cannot store a plaintext address or raw token. AES-256-GCM seals a normalized email in a fixed 1024-byte envelope; protocol version, purpose and requestId are authenticated metadata. Each record has a random 96-bit nonce. Tampering, wrong keys or swapped metadata fail closed. No raw recovery credential is encrypted/persisted: the future worker will issue tokens only when processing an intent, and action-token storage remains hash-only.

AUTH_RECOVERY_QUEUE_KEY is a separate random 32-byte lowercase hex secret, independent of CSRF/limiter keys. It has no default and is not configured/generated by this task. Keep it stable while pending records depend on it; rotation and restoration need a deliberate migration/key-retention plan. Database encryption does not protect against compromise of the application and its key together. Queued email addresses remain personal data despite encryption.

`scripts/db/recovery-requests.ts` explicitly provisions the strict contract, requestId uniqueness and lifecycle ordering indexes. Only disposable fixtures have used it; existing deployment commands/runtime do not auto-create this collection. Readiness checks are read-only and reject drift or any TTL bypassing audited lifecycle operations. The approved lifecycle below extends the earlier admission-only contract; delivery execution and operational visibility remain separate work. There is no automatic email send/retry, durable delivery promise or public timing-conformance claim.

### Guarded one-job delivery processing

`createRecoveryDeliveryWorker` now provides explicit `processOne` execution over the approved lifecycle. It claims/decrypts one intent, checks provider readiness, fences the live lease in the same transaction as account/token/audit issuance, then rechecks live ownership before calling the provider outside that transaction. Its internal `issueForDelivery` service primitive uses the same approved eligibility/version guards and reissue rules as existing recovery. Only an already-admitted persisted intent reaches this path; the approved request budget is not charged twice. Do not expose that lower-level issuance primitive directly through an HTTP handler.

Unknown/ineligible accounts complete in the same queue status without a send. Known pre-send failures become failed; a thrown send or uncertain acknowledgment becomes uncertain. After a finalization audit failure, the still-processing intent is not reclaimed or resent; expiry can later mark it uncertain. A process paused after its last lease check could still resume a send, so this does not promise exactly-once SMTP delivery or recall of a started request. The no-reclaim/no-resend policy prevents a competing processor from blindly repeating it.

The result reports only whether an intent was processed/finalized, never account eligibility, recipient, raw link, lease credential or a delivery guarantee. Raw links exist only between issuance commit and provider invocation. The new worker is not wired to application runtime, HTTP, CLI or a scheduler, and construction opens no mail connection. Tests use owned disposable databases and a mocked provider; no live Gmail send has occurred. Request HTTP admission, actual local deployment and live acceptance still remain separate work.

### Approved explicit worker lifecycle

The user approved RECOVERY_WORKER_POLICY_PROPOSAL.md on October 22, 2026. `createRecoveryRequestLifecycle` now provides explicit claim, live-lease check, transactional guard, finalize, expireOne and purgeOne operations. Admission timestamps are set with database time inside its transaction. Claim atomically selects the oldest non-expired pending intent, stores only a random lease credential's hash, and grants a two-minute lease. Processing intents are never automatically reclaimed. `guard` writes a bounded lease fence inside a caller transaction so future token issuance can serialize against lifecycle transitions; a read-only isLive check is not a substitute for that transactional guard. Neither check makes an external SMTP send atomic with the database.

Only the live lease holder can finalize completed/failed/uncertain. Every terminal transition removes ciphertext, nonce, tag and active lease credentials atomically with its audit record. Schema validation forbids terminal records retaining those payload fields. Pending requests older than 24 hours become expired, and expired processing claims become uncertain. A stale callback cannot change either terminal state. There is no requeue/resend method or background loop.

Terminal metadata gets an exact seven-day cleanup deadline. purgeOne deletes only an aged terminal queue record and writes a separate audit event in the same transaction; audit records and unrelated collections are never purged by it. A failed audit rolls back both state changes and deletion. Cleanup runs one record per explicit invocation, with no TTL index. **No scheduler is active**, so these primitives alone do not enforce real-world cleanup timing until a reviewed runner/sweeper is enabled. Only synthetic records have been processed/deleted in disposable fixtures.

The schema now includes state-dependent processing/terminal fields and lease/retention indexes. An existing queue needs the explicit deployment helper reapplied and verified before using this lifecycle; no external migration has been run. Worker token-issuance/delivery handoff, scheduler/operational access, request HTTP admission and controlled live acceptance remain next. Gmail credentials, reviewed password data and a queue encryption key are still required for activation.

Local completion HTTP handlers now exist at POST /api/v1/auth/reset-password and /api/v1/auth/verify-email, with GET /api/v1/auth/recovery-challenge?purpose=reset-password or verify-email. They return sanitized 503 by default. AUTH_RECOVERY_COMPLETION_HTTP=1 is an explicit local-only switch; production still refuses it, and missing Gmail/blocklist/storage prerequisites prevent service initialization. It does not enable UI, email-request endpoints or send any email. The legacy login/logout challenge endpoint remains unchanged. Synthetic UI acceptance still uses its isolated bridge until the full request flow is reviewed.

Enabled completion requires exact Origin, JSON, the purpose-bound nonce cookie/custom CSRF header and exact allowlisted fields: token for verification, token/password for reset. Streamed bodies are capped at 16 KiB before parsing. HTTP validation precedes service initialization; the shared service applies token/eligibility/expiry/limiter/password rules. Success returns only completed=true. A committed password reset clears this browser's session cookie; failed attempts retain cookies, and verification does not clear an unrelated browser's cookie. Responses are no-store with server-generated request IDs and genuine limiter Retry-After values. The handlers expose no delivery operation.

Email-request HTTP endpoints remain absent. Synchronous eligible-only Gmail send failures must not become an account-existence signal; this is still an unresolved request-delivery boundary, not fixed by hiding error messages. The completion-only slice makes no account-enumeration or live-email acceptance claim. Leave the switch unset until prerequisites and a controlled acceptance plan are ready.

The internal `getLocalRecoveryService` now composes local HTTPS settings, Gmail configuration, the checksum-pinned blocklist, existing infrastructure/identity/session/limiter readiness and the shared guarded recovery orchestration. It validates mail/blocklist settings before opening database access, shares concurrent initialization and permits retry after initialization failure. Initialization never verifies SMTP credentials or sends mail. Failed service initialization closes its mail adapter. Configuration/list changes require restarting the server to replace the successful cached snapshot.

`createTestRecoveryService` retains its synthetic database guard; `createLocalRecoveryService` separately requires the approved local HTTPS configuration and a Gmail adapter plus prevalidated password validator. Both use the same token/account/session/audit transaction implementation. These factories are internal service boundaries, not safe public HTTP handlers. Only the explicitly gated completion handlers import the recovery runtime. Provider-specific send failures can still differ by account eligibility and must be addressed before exposing email requests. Missing local credentials or a reviewed list remain SERVICE_UNAVAILABLE; there is no permissive fallback.

The sender mailbox can be changed through GMAIL_USER in ignored .env.local without a code change. Its app password must belong to that same Google account. Changing the sender does not validate an existing credential or trigger a connection/send.

Unit tests use a mocked SMTP transport and synthetic addresses/credentials. They cover credential/configuration rejection, lazy startup, readiness, recipient/header injection, purpose/origin validation, provider failure sanitization, acceptance checks and no automatic retries. No live Gmail verification or email has been performed. Google may still reject a credential/account or sender at runtime; these checks do not prove delivery/inbox placement.

Real-user recovery remains disabled. Remaining work includes release blocklist provenance/coverage, guarded non-test service wiring, actual bounded/CSRF-protected recovery HTTP adapters, same-response account-enumeration defenses around provider failures, explicit deployment/readiness and controlled live acceptance. The sender/password alone does not approve hosted ingress or production release.

## Local password-blocklist loading

`loadPasswordBlocklist` is a lazy server-only loader for a separately reviewed local UTF-8 artifact. Configure AUTH_PASSWORD_BLOCKLIST_PATH as an absolute file path, AUTH_PASSWORD_BLOCKLIST_SHA256 as its lowercase SHA-256 and AUTH_PASSWORD_BLOCKLIST_SOURCE as a nonempty source/version reference. Hash the exact file bytes, including line endings, with PowerShell `Get-FileHash -Algorithm SHA256 -LiteralPath <path>` and lowercase the returned hash before configuring it. Changing line endings requires deliberately updating the pinned checksum after review.

The file format is one whole password per line (LF or CRLF), no comment syntax, empty delimiter lines ignored and spaces preserved. The loader refuses missing/unreadable/non-regular files, checksum drift, invalid UTF-8, control characters, empty lists, files over 16 MiB and more than one million entries. Reads are bounded from one descriptor even if a file changes size during loading. A loaded validator keeps its snapshot; a reviewed list update requires service reinitialization. Errors are sanitized and there is no fallback list or network lookup.

The checksum proves artifact integrity against the configured digest; the source string is an operator assertion, not proof of provenance or coverage. No release dataset has been supplied or approved by this loader task, and it is not wired into public recovery. Licensing, long/common/compromised-passphrase coverage, refresh cadence and review evidence still need an actual artifact. Tiny synthetic fixture lists are not a release blocklist. No user password or candidate digest is transmitted by the loader.
